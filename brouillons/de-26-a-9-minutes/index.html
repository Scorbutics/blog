Mes vérifications ralentissaient mes agents : de 26 à 9 minutes

Brice Bulgarelli · brouillon du 15 novembre 2026

Brouillon. Première version, non publiée : le texte et les chiffres peuvent encore changer. Merci de ne pas la diffuser sans me demander.

Dans l'article précédent, j'expliquais que je ne lis plus le code front que l'agent écrit : je fais confiance à un vérificateur, motu, qui rejoue chaque état déclaré de l'application dans un vrai navigateur.

Sauf qu'un vérificateur, ça a un coût. Et ce coût a fini par me rattraper.

1. Le constat

Sur mon application principale (80 "islands", 23 "regions", 91 flows déclarés), un motu check --runtime complet prenait 26 minutes. Et la version statique, celle censée tourner à chaque modification, prenait déjà plus de deux minutes.

Le problème, c'est que les instructions que je donne aux agents leur demandaient de lancer ce check complet "une fois, avant de rendre la main". Résultat : chaque tâche, même une petite correction sur un seul écran, se terminait par une demi-heure d'attente. Les agents passaient plus de temps à attendre motu qu'à coder.

Pire : ce temps ne dépend pas de ce qu'on a changé. Il grossit avec la taille de l'application. Plus le projet avance, plus chaque tâche coûte cher.

2. Mesurer avant de construire

Leçon retenue de Seam : avant de coder la moindre optimisation, je regarde où part réellement le temps.

Le check tourne avec un mode --verbose qui chronomètre chaque étape. Sur les 26 minutes :

PosteTemps
Flows des régions (dont mutants)634 s
Rejeu "island nulle" (173 scénarios)301 s
Hors de toute étape chronométrée476 s (31 %)

Deux choses sautent aux yeux :

  • Tout est séquentiel. Un seul serveur, un seul navigateur, une seule page, qui enchaîne les 103 cibles une par une. Sur une machine à 12 cœurs.
  • 31 % du temps n'est mesuré nulle part. En creusant : chaque lecture d'un fichier de scénarios (*.evidence.ts) lance un process Node + tsx, environ 1 seconde. Et le même fichier était relu jusqu'à quatre fois par région. Quelques centaines de secondes à relire des fichiers qui n'avaient pas changé.

Mais la vraie question, avant tout ça : combien de ces 26 minutes servent réellement à quelque chose ?

Si je modifie un composant de la page "profil", re-vérifier les 22 autres régions ne m'apprend rien. Leur résultat ne peut pas avoir changé.

3. Le cache : ne pas re-prouver ce qui est déjà prouvé

L'idée

Le verdict d'une région dépend d'un ensemble fini de choses : les fichiers que le navigateur charge pour l'afficher, la version de motu, la version du navigateur, la configuration, les options du check. Rien d'autre, puisque tout tourne sur des fixtures avec un backend simulé.

Donc si aucune de ces entrées n'a bougé depuis la dernière fois où le check a réussi, le résultat sera le même. On peut le rejouer au lieu de le recalculer.

C'est le principe d'un cache de build (Bazel, Turborepo, Nx...), appliqué à des tests navigateur.

Pourquoi pas simplement git diff ?

motu avait déjà une option --changed, basée sur git : "quels fichiers ont changé, et à quelle island appartiennent-ils ?". Le souci, c'est qu'elle ne raisonne que sur les chemins : un fichier qui n'est pas dans le dossier d'une island (la page, un utilitaire partagé, un fichier de fixtures commun...) ne peut être attribué à personne, et dans le doute, tout est relancé. En pratique, presque à chaque fois.

Ce qu'il faut, ce n'est pas "où est le fichier", c'est "qui l'importe".

Simuler avant de coder

Avant d'écrire le cache, j'ai fait une simulation rapide : construire le graphe d'imports de chaque island et de chaque région (avec esbuild, qui sait résoudre les alias exactement comme le bundler), puis rejouer les 293 derniers commits du projet pour voir ce que chacun aurait invalidé.

Résultat :

  • 61 % des commits ne touchent que du code applicatif. Ceux-là n'invalident en moyenne que 4 régions sur 23 et 12 islands sur 80. Environ 83 % du travail évité.
  • 39 % des commits invalident tout : une mise à jour de motu lui-même, ou un fichier global (configuration, dépendances).

=> Sur l'historique complet, le cache aurait évité environ la moitié du travail. Pour un développeur qui travaille sur une fonctionnalité, c'est bien plus.

L'empreinte

Concrètement, pour chaque cible, motu calcule une empreinte (un hash) de tout ce dont son verdict dépend :

  • le contenu de chaque fichier de son graphe d'imports (y compris le code de l'application, pas seulement celui de motu) ;
  • les islands d'une région, et les régions avec lesquelles elle compose ;
  • les versions des packages qu'elle importe ;
  • la version de motu, du navigateur, la config, et les options du check.

Le calcul de toutes les empreintes du projet prend 1,8 seconde (la première version prenait 7,7 s : elle relisait chaque fichier une fois par graphe qui le contenait).

Et la preuve que l'attribution est juste, en modifiant temporairement un fichier à la fois :

Fichier modifiéEmpreintes qui changent
Le fichier de scénarios d'une régioncette région, et rien d'autre
Un composant de l'applicationles 3 régions qui l'importent réellement
lib/utils.ts, importé partouttout le projet (c'est voulu)

Les règles qui rendent le cache honnête

Un cache de tests, c'est dangereux : un résultat faux rejoué indéfiniment est pire qu'un test lent. Quatre règles :

  • Seuls les verdicts propres sont gardés. Une erreur, ou un check qui n'a pas pu tourner, est toujours relancé. Un test instable ne doit pas devenir un échec permanent.
  • Un rejeu n'est jamais silencieux. Chaque ligne rejouée le dit : · runtime replayed — inputs unchanged since proved 3h ago, et le verdict final compte ce qui a été re-prouvé et ce qui a été rejoué.
  • Ce qui lit l'horloge est re-prouvé chaque jour. Un composant qui appelle new Date() peut s'afficher différemment demain : sa date fait partie de l'empreinte.
  • Une seule option pour tout relancer : --no-cache. Et --max-age 7d pour re-prouver périodiquement ce qui est rejoué depuis trop longtemps.

Résultat sur une région inchangée : 72 s → 21 s.

4. Le check statique : la même erreur, en plus petit

En profilant le check statique (celui qui tourne à chaque modification), j'ai retrouvé exactement le même schéma que dans le runtime : du travail refait pour rien.

La vérification d'intégration parcourait l'arbre syntaxique de tous les fichiers de l'application, quatre à cinq fois, pour chacune des 23 régions. 78 secondes sur 106, passées à relire les mêmes fichiers.

Trois caches, de quelques lignes chacun :

  • parcourir l'arbre de chaque fichier une seule fois par type de nœud ;
  • lire les déclarations de régions une fois, tant qu'aucun fichier concerné n'a changé ;
  • retirer les commentaires d'un fichier une seule fois, au lieu d'une fois par région.

Résultat : 147 s → 33 s. Et pour m'assurer que rien n'a changé dans les résultats, j'ai comparé la sortie JSON complète avant et après : identique, section par section.

5. Les workers : utiliser les 12 cœurs

Le cache ne sert à rien sur un run "à froid" : la CI de nuit, ou après une mise à jour de motu. Là, il faut que le run complet lui-même soit plus rapide.

Le plus gros levier était évident : tout tournait sur un seul navigateur, une page après l'autre.

Pourquoi des process, et pas du parallélisme dans le même process

Le code qui pilote le navigateur garde de l'état global : la page en cours, les journaux de diagnostic, quelques délais. Le rendre parallélisable aurait demandé de tout réécrire.

Plus simple : lancer plusieurs workers, chacun dans son propre process, avec son propre serveur et son propre navigateur. Le process principal garde la main sur tout le reste :

  • il distribue les cibles par une file d'attente, les plus longues d'abord (pour ne pas finir avec une grosse région qui démarre en dernier) ;
  • les workers lui renvoient leurs résultats sous forme de données ;
  • c'est lui seul qui affiche, ordonne et décide du code de sortie. Un run parallèle se lit exactement comme un run séquentiel.

Deux pièges

  • Le cache de dépendances de Vite. Au premier démarrage, Vite pré-compile les dépendances dans un dossier partagé. Quatre process qui le font en même temps, c'est une course. Solution : le premier worker démarre seul, sur la cible la plus petite, et les autres attendent qu'il ait répondu.
  • Un worker qui meurt. Sa cible n'est ni "réussie" ni "échouée" : elle est marquée INCONCLUSIVE (code de sortie 2 : "relancez, ne corrigez rien"). Un agent qui lit un échec cherche un bug ; il ne faut pas lui en inventer un.

Par défaut : la moitié des cœurs, plafonnée à 4 et limitée par la mémoire disponible, et un seul worker quand il y a peu de cibles (démarrer un worker coûte une quinzaine de secondes).

Résultat sur 4 grosses régions et leurs 31 islands : 410 s sur 1 worker, 177 s sur 4, avec des verdicts identiques sur les 103 cibles.

Et sur le run complet, à froid, caches vidés : 26 min → 8 min 56.

6. Ce qui a changé dans la façon de travailler

Le gain de temps est une chose. Le vrai changement, c'est la règle donnée aux agents :

  • Pour terminer une tâche : le check statique (motu check, une trentaine de secondes) et la vérification d'intégration.
  • Quand on ajoute ou modifie une partie de l'écran : un check navigateur ciblé sur ce qu'on a construit, motu check --region <id> ou --island <nom>. Le reste du projet reste vérifié statiquement dans le même run.
  • Le run complet (motu check --runtime) n'est plus jamais lancé par un agent. C'est le travail de la CI, la nuit.

=> Le coût d'une tâche dépend maintenant de ce qu'elle touche, plus de la taille du projet.

7. Limites

  • Le run complet n'est pas vraiment comparable. Les 26 minutes ont été mesurées avec la version de motu embarquée dans le projet, les 8 min 56 avec la version de développement, qui fait échouer certains flows de cette application (une incompatibilité que j'ai trouvée en chemin, et qui existe sans mes changements). Ce qui est garanti : sur les mêmes cibles, 1 ou 4 workers donnent exactement les mêmes verdicts.
  • Le cache ne voit que ce qu'on lui donne. Tout ce que l'empreinte ne capture pas (une variable d'environnement hors MOTU_*, une donnée lue au runtime...) est un angle mort. D'où --max-age : re-prouver régulièrement, même sans changement.
  • Un fichier partagé invalide tout. Modifier lib/utils.ts relance tout le projet. C'est juste, mais c'est là que les workers restent indispensables.
  • Il reste du gras. Le rejeu "island nulle" coûte encore environ 300 secondes, et chaque scénario attend des délais fixes. Ce sera pour une prochaine fois.

8. À vos tests

  • Le commit : 45c8c91 sur motu, perf(check): replay unchanged runtime verdicts, scope the browser pass, run it on lanes.
  • motu check --region <id> : le navigateur sur une région, le statique sur tout le reste.
  • motu check --runtime --jobs auto --verbose : le run complet sur plusieurs workers, avec le temps de chaque cible.
  • motu check --runtime --no-cache : tout re-prouver.
